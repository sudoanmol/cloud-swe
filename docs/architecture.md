# Architecture

The authority on design, security boundaries, decisions and implementation status. [`mvp.md`](mvp.md) owns delivery scope and priorities, [`effect.md`](effect.md) records how Effect is used, and [`AGENTS.md`](../AGENTS.md) holds the working rules. Package READMEs describe their code's contracts; if one disagrees with this file, this file wins and the README gets fixed.

### Backlog details and release placement

Requested 2026-10-29, originally recorded under slice 1; these are requirements, not completed features. [`mvp.md`](mvp.md) now separates MVP from V1 and owns their delivery placement. Automatic and manual compaction are in the MVP; the other additions below are V1 unless explicitly reprioritized. Architectural slices and release phases are not interchangeable. Follow the protocol-first build order in [`AGENTS.md`](../AGENTS.md).

- **Conversation tree/history navigation:** select an earlier conversation point using Pi tree-style navigation and replace the session's active conversation context with that selection. Keep the previous branch available for later navigation; do not merely open a read-only history view or run two active writers. Default to **conversation-only reversal**, leaving sandbox files unchanged. The UI may offer a separate, explicit code-reversal choice if a suitable filesystem/Git checkpoint exists. Conversation navigation does not itself restore code or a sandbox snapshot, and must not introduce automatic snapshots. Verify the Pi Durable branch/head integration rather than assuming coding-agent's tree API is interchangeable.
- **Automatic and manual compaction (built):** Pi-native automatic compaction against a 500K usable window (`cappedContext` in `server/src/sessions/models.ts`, because long-context models degrade past that) and `POST /v1/sessions/:sessionId/compact` with optional instructions. Report compaction progress/completion/failure through snapshot/SSE, preserve navigable history, and test interruption/restart and queued-message behavior. Use Pi's compaction machinery, not a second summarization loop.
- **Image attachments:** accept images from the client, retain attachment references in conversation history, and send supported image content to the selected model. Evaluate **R2 for image bytes**; storage choice and retention are not yet settled. Keep large image bytes out of DO transcript rows, enforce authenticated access and upload size/type limits, and preserve attachment availability across reconnects/restarts.

- **Native interaction tools (built):** `ask_user_question` (`server/src/tools/questions.ts`, durable records in Thread storage, answer route, `Session.questions`) and `todo` (`server/src/tools/todo.ts`, a rewindable Pi document, `Session.todos`), based on `rpiv-ask-user-question` and `rpiv-todo`. Pi package parity stays out of scope (2026-10-30): coding-agent extensions don't run unmodified on Pi Durable. Plannotator is deferred, and Paper's MCP is deferred until Paper ships a remote MCP.
- **Client terminal:** let the authenticated client open/control a terminal in its session's sandbox, independent of model tool calls. Support streamed output, input, resize, termination and reconnect with explicit process identity. Stop/resume and lost execution receipts must report interruption/uncertainty rather than imply a shell survived or blindly rerun a command. The terminal receives no upstream Git/model credentials and cannot target another session's sandbox.
- **Port preview URLs:** expose running sandbox services to the client through E2B port URLs, which need an access token and keep their host across a resume (see [`infra-decisions.md`](infra-decisions.md#10-port-urls-across-sessions)); scope access to the owning session, surface stopped/unreachable services, and handle URL changes on resume. Do not expose arbitrary ports publicly by default or embed upstream credentials in preview URLs. Explicit public sharing, if needed, is a separate opt-in policy.
- **Computer use and browser automation:** integrate computer use (E2B's Desktop sandbox is untested) and install/support `agent-browser` for CLI-driven browser automation inside the assigned sandbox. Project actions, results and screenshots to the client; reuse the image-attachment storage/access policy where appropriate. Verify template dependencies and browser/display lifecycle, and distinguish browser automation from desktop control. This controls the sandbox, not the user's own machine or browser. No Git/model credential injection is implied.

## Workspaces

Status: **build step 1 done** (fresh sandbox per session). Later steps are designed, not built.

Agents run in parallel, each in its own E2B sandbox. E2B is the only provider; inside `pnpm test` a Docker test double stands in for it. E2B's specifics and test results are in [`infra-decisions.md`](infra-decisions.md#13-sandbox-provider). Concurrent agents editing one checkout corrupt each other through a shared Git index and working tree (see [Agent-to-agent communication](#agent-to-agent-communication)), so one sandbox per session gives one writer per filesystem without lease bookkeeping. V1 attach and subagents share a sandbox between threads (see [Decisions](#decisions)). Codex cloud tasks and Cursor background agents follow the same pattern.

### Ownership

| State                                                                  | Authority                                                                                                                                                                                    |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Which sandbox a session uses, its lifecycle state, the concurrency cap | `Catalog` DO (workspace records next to session records)                                                                                                                                     |
| Pi transcript, runs, tool tasks                                        | The session's `Thread` DO                                                                                                                                                                    |
| Files, processes, Docker data                                          | The E2B sandbox                                                                                                                                                                              |
| Templates: base image, env vars, setup                                 | E2B templates (`cloud-swe`, built by `server/scripts/e2b-template.ts`), selected by name through `WORKSPACE_TEMPLATES`. A template must not pass Git or model credentials into its sandboxes |

A workspace ID is an application UUID. It maps to E2B's sandbox ID on the server, and the two stay distinct. A restored or forked workspace gets a new sandbox under a new workspace record.

### Records

```ts
Workspace {
  id: WorkspaceId;               // app UUID, minted with the creation intent
  sessionId: SessionId;          // exactly one session per workspace
  template: string;              // allowlisted E2B template name
  source: { kind: 'fresh' } | { kind: 'fork'; workspaceId: WorkspaceId } | { kind: 'snapshot'; snapshotId: SnapshotId };
  sandboxId: string | null;      // null until E2B returns it
  state: 'provisioning' | 'ready' | 'stopped' | 'deleted' | 'failed' | 'uncertain';  // stored as WorkspaceEntry: running | stopped | deleted
  lastActiveAt, createdAt, updatedAt: Timestamp;
}

Snapshot {                       // only created when the user asks
  id: SnapshotId;
  workspaceId: WorkspaceId;
  providerSnapshotId: string;
  createdAt: Timestamp;
}
```

`uncertain` means a create may have happened but its sandbox can't be identified: no sandbox ID was recorded and the metadata lookup found more than one match or a truncated result. Never assume it didn't happen; surface it.

### Session creation

The client stops sending `workspaceId`. It names an allowlisted template and may optionally request an initial repo/branch, or a source to fork or restore from. Neither repo nor branch is required: an agent can clone repositories later. Track the repository inventory and optional base assignment in session metadata, separate from workspace identity; changing the base does not delete other checkouts:

```json
{ "operationId": "…", "engine": "pi", "target": "cloud", "template": "cloud-swe",
  "repo": { "url": "https://github.com/…", "branch": "main" }, "model": { … } }
```

To fork or restore, the request sends `"from": { "session": "<sessionId>" }` or `"from": { "snapshot": "<snapshotId>" }` instead of `template` and `repo`.

1. Validate the request. Unknown templates are rejected (400), and so are requests over the concurrency cap (`busy`, 409).
2. In one storage write, persist the creation intent with a fresh `sessionId` and `workspaceId`, plus the workspace record in `provisioning`.
3. Create the sandbox from the template, tagged with the workspace ID in its metadata. E2B has no idempotency key, so before any create without a saved sandbox ID the server lists sandboxes by that metadata, and concurrent retries in the catalog share one lookup and create. More than one match fails closed as `sandbox_creation_unconfirmed`. Fork and restore from a snapshot are not built.
4. Record the sandbox ID, then wait for a ready state (`inspectWorkspace` maps E2B's states).
5. Open the `Thread` DO and PiHarness root, then index the session.

Retries of the same operation resume from whichever step was last committed. A changed intent under the same ID is still 409.

Admission commits the intent under `blockConcurrencyWhile`; provisioning runs outside it, so parallel creations do not queue behind each other.

Create errors (the rest are in [`infra-decisions.md`](infra-decisions.md#13-sandbox-provider)):

- Timeouts and 5xx: a sandbox may exist, so the provisioning marker keeps holding a cap slot and the retry looks it up by metadata first.
- An authentication error or other definite refusal: nothing exists. The marker is deleted at once and the client sees `sandbox_refused`.

### Lifecycle

```text
provisioning -> ready <-> stopped -> deleted
                deadline pause        SANDBOX_DELETE_AFTER_DAYS without activity
                (resume on message)
```

- **Running:** a sandbox pauses at its deadline instead of dying, and pausing keeps files and processes. Hobby caps a run at 1 hour, reset by resuming, so a durable `KeepAlive` job in the Thread (same pattern as `CommandReconciler`) runs while a run is active and every `KEEPALIVE_INTERVAL_SECONDS` (120) connects, which resumes the sandbox and raises its deadline. Every file or command call connects too, which is what carries a polled command past the hour, so only calls that may run the sandbox reach it. When the run ends, one final 10-minute deadline (`IDLE_TTL_SECONDS`) lets the sandbox pause soon, so a finished session frees its slot; a failed final update is retried by the same job. Each message re-arms the job. Per-tick additions go in `keepAliveTick` (`server/src/sessions/keep-alive.ts`).
- **Stopped (paused):** the deadline is the only idle stop. A paused sandbox keeps its disk and processes. The catalog stores a believed state per workspace (`running` counts toward the cap) and corrects it against E2B whenever it matters: a state read (cached 15 s), a resume, or a full cap. Clients see `workspace.state` live: `starting`, `running`, `stopped`, `deleted`, `unreachable`. Tools refuse a deleted workspace with a clear message.
- **Resume:** a message for a paused sandbox resumes it (`connect`), reports `starting` until ready, then reconciles before admission. Open commands are still running, so they stay open. A retry of an already-admitted message never resumes. If `MAX_SANDBOXES` are running, the message fails with 409 `sandbox_limit_reached` and nothing is resumed. A sandbox E2B no longer knows is treated as deleted.
- **Deleted:** a catalog alarm deletes the sandbox after `SANDBOX_DELETE_AFTER_DAYS` (7) without activity (keep-alive ticks and messages count as activity). E2B keeps a paused sandbox with no limit, so this alarm is the only cleanup. The transcript stays in its Thread DO. Open commands in a deleted sandbox end as `lost` with a truthful reason.
- **Replacement:** a message for a session whose sandbox is deleted gets a **new, empty sandbox** under a new workspace record bound to the same session. The replacement is keyed by the deleted workspace, so concurrent or retried messages share one, and it follows the creation rules (cap, metadata lookup, provisioning marker). The Thread rebinds `session.workspace.id` and queues a notice in the same write. The message that is admitted next carries the notice as a separate native Pi passive entry (`cloud-swe.notice`, written with `Conversation.submit({ type: 'write' })` just before the input), so it is never the user's text, never in the stored request or receipt, and hidden from client snapshots, history and SSE. It is built by `sandboxReplacedNotice(repos)` in `server/src/sessions/notice.ts`. An ordinary resume never produces a notice.
- **Snapshot (user action):** `POST /v1/sessions/:sessionId/snapshots` saves a named snapshot of a ready or stopped sandbox. `DELETE /v1/snapshots/:snapshotId` removes it. Snapshots are never created or deleted automatically.

### Cost and the concurrency cap

E2B's prices and limits are compared in [`infra-decisions.md`](infra-decisions.md#13-sandbox-provider). On Hobby, the `cloud-swe` template's 4 vCPU and 8 GB cost about $0.33 an hour from a one-time $100 credit, and a paused sandbox costs nothing.

- **The real limit is hours, not concurrency.** At 10 hours a month the credit lasts about 30 months.
- **Default cap:** `MAX_SANDBOXES=4` running sandboxes. Raise it if your usage allows.

## Repository access

No Git credentials enter a sandbox: not in its files, env vars, commands or template. An agent controls its sandbox's shell, so anything placed there is usable without the tool boundary.

- **Empty and multi-repo sessions:** no repo/branch is required at creation. The agent may clone multiple public/private repositories later and designate or change one optional base repo. Non-base checkouts remain usable. The base is working/PR context, not a single-repo filesystem restriction or an automatic permission grant.
- **Public repos:** clone anonymously over HTTPS. Public checkouts need not all use the same host. The planned private-credential broker supports GitHub; other private hosts require their own provider integration, not forwarding a GitHub PAT to arbitrary URLs.
- **Git identity:** each checkout's `user.name` and `user.email` are the app's bot, `cloud-swe[bot]` and `332717987+cloud-swe[bot]@users.noreply.github.com`, in GitHub's `<id>+<name>[bot]` format. A `prepare-commit-msg` hook adds a `Co-authored-by` line for the allowed GitHub account. It sits in `.git/hooks` and is also registered as a config-defined hook (`hook.cloud-swe-co-author.*`, Git 2.54+), because a repo whose setup sets `core.hooksPath`, as husky's `prepare` script does, would otherwise skip `.git/hooks` and silently drop the credit; `addIfDifferent` keeps the line single when both run. The E2B template installs Git from the git-core PPA for this; the Docker test image's older Git only covers the `.git/hooks` path. The account is read at sign-in with its user token (`GET /user`), and the line always uses its `<id>+<login>@users.noreply.github.com` address. Identity values are not secrets, so they may enter the sandbox; tokens may not. The agent, or a repo script that rewrites Git config, could remove either hook, which only loses the credit.
- **Personal auth:** a GitHub App, self-hosted by one user, with repositories picked at install. The Worker holds its private key (`GITHUB_APP_PRIVATE_KEY`, PKCS#8) and client ID as secrets. `Credentials.githubToken(owner, repo)` finds the repo's installation and mints a token limited to that repo, kept in memory and replaced 15 minutes before expiry. A repo without the app gets no token, so public repos stay anonymous and PR tools say the app is not installed.
- **Implemented (2026-10-30), private repos and pushes:** `git_clone {url, branch?, path?}` registers the repo in Thread storage (`Session.repos`, authorization = registered), then clones in the sandbox through the command path. `CreateSessionRequest.repo` registers one repo as base, in the same Thread write as the session, and starts a detached, unreconciled clone. The default directory is the repo name without leading dots or dashes (`.github` clones to `github`); a repo with no usable directory is refused with 400 before anything is created; `git_clone` is idempotent and finishes it. GitHub URLs (`https://github.com/owner/repo`, canonicalized to lower case) go through the proxy; other public https hosts clone directly. No ssh, no embedded credentials, every value shell-quoted.
- **Proxy:** `/git/:sessionId/github.com/:owner/:repo.git/{info/refs,git-upload-pack,git-receive-pack}` is mounted before bearer auth and the body limit and streams bodies. It needs `PUBLIC_URL`. The sandbox git config (`$ROOT/.cloud-swe/git.config`, included from the global config) rewrites `https://github.com/` to the proxy and sends `Authorization: Bearer <capability token>`, so `origin` keeps its readable URL. The token is random, stored only as its SHA-256 with a 1 h expiry in the Thread. A rotation by `refreshGitAccess(host)` keeps every unexpired earlier token valid (newest 16), so a clone that outlives several rotations finishes. It runs at message admission and from the keep-alive during long runs, and `git_clone` rotates only when the token is near expiry or the sandbox has no config file (a replaced sandbox). Unauthenticated, expired, foreign-session or unregistered-repo requests get 401/403 with no upstream call. Upstream is only `https://github.com/<owner>/<repo>.git/...`, redirects are refused. The Worker adds the repo's installation token (Basic) upstream, anonymously when the app is not installed there.
- **Push policy** (parsed from the pkt-line command list; the pack is never read): exactly one command, ref `refs/heads/cloud-swe/<slug>-<first 8 of session ID>`. Refusals are `ng` reports git prints. Deleting a branch or tag, or creating a tag, is also refused, and files a `ref_change` approval whose deterministic ID names the exact change, so a retry files nothing new and a blocked push isn't asked again. Moving a tag has no approval path. A non-fast-forward update is forwarded, checked with the compare API, restored with a forced `PATCH` on the ref and reported as `force push requires approval: use git_request_ref_update`. Ceiling: the branch briefly shows the forced commit, and the rejected commit stays on GitHub for the approval path. Pack parsing is the upgrade path. There is no `git_push` tool.
- **PR tools** (native Pi tools in the Worker; the installation token never leaves it; codemode gets them): `github_pr_create` (head must be a session branch, looks up the open PR before and after a failure), `github_pr_update`, `github_pr_close`, `github_pr_reopen`, `github_pr_comment` (embeds `<!-- cloud-swe:<callId> -->` and searches for it first), `github_pr_read` (bounded). The `repo` argument must be registered; it defaults to the base. They may read and act on any PR in a registered repo, not only the session's own (2026-10-30): a session can have several branches and PRs, and often needs to read others.
- **Approvals** (Thread storage, `Session.approvals` carries open plus recent): `git_request_ref_update {repo, sha, targetBranch, force}` and `github_pr_merge {repo, number, method}` (a merge commit unless `method` says otherwise) file a pending approval and return at once. `expected` (target branch tip, or PR head at request time) is the lease; a merge also leases the PR's base branch (`baseRef`, shown to the user), because `github_pr_update` can retarget it. Only `POST /v1/sessions/:sessionId/approvals/:approvalId` executes: `executing` is persisted before dispatch, the lease is re-read, a definite GitHub refusal is `failed`, and a lost or ambiguous response is `unknown`. Ceiling: the lease is check-then-act, because GitHub's REST ref API has no compare-and-swap, so a push between the read and the update is overwritten; a receive-pack with `old = expected` is the atomic upgrade path (a PR merge's `sha` is checked by GitHub itself). A repeated approve then reconciles by reading the ref or PR and never re-sends blindly. Each outcome (decided, or `unknown`) reaches the agent as one `followUp` message whose deterministic operation ID names the approval, state and result. If the session refuses or fails to admit it, the durable `FollowUpDelivery` Lifecycle job in the Thread retries every 15 s until admitted; it only delivers and never touches GitHub. Question answers use the same job. No auto-approve and no expiry in the MVP.
- **Session PRs:** `Session.pullRequests` lists PRs from session branches with their last known state, updated by PR tools (including `github_pr_read` view) and merge approvals. A PR changed directly on GitHub stays stale until the next such call.
- The original cloud-swe's bundle staging and push approvals are deferred until there's a need for review before every push.

## Environments and network secrets

An environment is a named, account-level set of secrets in the `Credentials` DO, chosen per session ([infra-decisions §8](infra-decisions.md#8-environments-and-secrets)). Normal secrets (variables) are visible to the client and the agent, and reach agent commands through `.cloud-swe/env.json`, which the command supervisor reads at start. Network secrets are write-only: the sandbox holds a placeholder, and the real value is swapped in by the Worker's `/net` route after the request leaves the VM ([§9](infra-decisions.md#9-how-network-secrets-reach-the-outside)). [`network-secrets.md`](network-secrets.md) walks through the swap step by step, with the code for each step.

**Boundary:** the platform never delivers a network-secret value to sandbox files, env vars, commands, Thread or Pi records, or logs. The daemon's config holds the session's network token, which is a capability, not a credential: it lets calls reach the approved hosts until the sandbox is replaced or deleted. What this doesn't cover: a process in the VM can use the key on approved hosts during the session, and an approved host that echoes request headers returns the key. Approved hosts must be trusted, and the client says so.

## System prompt

`server/src/prompts/system.md` is the prompt Pi receives; `server/src/prompts/tools/*.md` are Pi's descriptions of read, write, edit and bash in Pi's format, reworded only to place them in the remote sandbox (read drops images, which remote reads don't support yet). Internal limits stay out of descriptions; the error reports a limit when it's hit. Wrangler bundles them as text modules. Git, PR and web tool descriptions live next to their tools.

## Model authentication

**Implemented:** authenticated `PUT`/`GET`/`DELETE /v1/credentials/models/anthropic` set, inspect metadata for, and disable the account's key in a private `Credentials` DO. The read-only Pi adapter resolves that key afresh for auth/model requests, so existing Threads see rotation without restart. The optional `ANTHROPIC_API_KEY` Worker binding is a development/testing fallback only; an explicit deletion persists a disabled marker and never reactivates that fallback. Pi explicitly registers the Anthropic provider; ambient environment/file credential resolution is disabled. A session stores an allowlisted model selector (`MODEL_PROVIDER` / `MODEL_ID`). Creation makes no model request. Message admission checks credentials and catalog membership before reserving a run; the selected provider/model are part of the saved intent. Provider stream errors and throws become generic diagnostics before Pi can persist them. Message/receipt endpoints and native run-state projection are implemented; steering and follow-up admission use Pi's native inbox, with at most 100 pending inputs. Cancellation targets a native input by its saved operation ID. Snapshot/history/SSE now project Pi's transcript without copying it into another store. Native entry IDs are session-scoped opaque strings, not fabricated UUIDs; historical run attribution may be null rather than invented. Native Pi file/shell tools execute against session-bound sandbox adapters, with remote command recovery and tool projection verified in Docker.

**Storage and integration:**

- The same Worker hosts APIs and the private account `Credentials` DO; there is no separate broker service. The current single-user bearer identity maps to `personal`. Future per-user names must derive from verified server identity, never a caller-supplied user ID.
- Credential writes return metadata only, with `Cache-Control: no-store`. Keys never enter session/Thread/Pi records. No API can read a stored key back.
- The read-only pi-ai `CredentialStore` resolves through the private DO binding and passes to `createModels({ credentials })`. `ANTHROPIC_API_KEY` remains optional for local testing (`wrangler secret put`; root `.env`).
- The model allowlist stays `MODEL_PROVIDER=anthropic` plus `MODEL_ID`.

Rules:

- The key is never returned or logged, and never enters a sandbox. Model calls run in the Thread DO; only tools execute in the sandbox.
- A submission is rejected before reserving compute if its provider has no credential.
- The provider and model are part of a submission's idempotency identity.
- Provider errors are sanitized before Pi checkpoints are saved.

**V1, client-initiated ChatGPT sign-in for Pi:** the client starts and completes Pi's supported provider authorization interaction through authenticated server endpoints; do not treat model-provider sign-in as application login. Expose auth progress/status, disconnect and reauthentication without exposing tokens. OAuth tokens expire, and pi-ai saves the refreshed tokens. Extend the existing `Credentials` DO and Pi adapter with serialized refresh/write support rather than creating a second service. It's the same pi-ai interface, so callers don't change. DO input gates make refreshes happen one at a time (replacing the original's Postgres advisory lock), and device-login state lives in the DO. The original cloud-swe model broker (`~/Developer/cloud-swe`, `docs/backend-contract.md#model-broker`) is the reference.

## Architecture research

Everything below is the original architecture evaluation, merged from the former `PLAN.md`. Its decisions stand unless [Decisions](#decisions) overrides them.

### Requirements established

- Personal use first.
- Pi for API-key model access. Anthropic API keys for MVP; V1 adds client-initiated ChatGPT sign-in for Pi.
- E2B for Linux workspaces (see [`infra-decisions.md`](infra-decisions.md#13-sandbox-provider)).
- Parallel agents: the server provisions one sandbox per session, so concurrent tasks never share a filesystem. See [Workspaces](#workspaces).
- A native, agent-agnostic UI eventually, not merely a remote terminal.
- Build the server first. iOS, other clients, and an MCP server come later.

### Recommendation

Keep the original Cloudflare control plane and Pi Durable execution model; sessions run Pi only. Pi Durable already supplies the underlying durable conversation/task primitives and working foreground/background subagent examples.

Use a small application-owned session API to present the runtime consistently. Agent-agnostic presentation does not imply an agent-agnostic backend implementation: the adapter must retain its engine's conversation, permission, interruption, and resume semantics.

The most important invariant: **one authority runs each engine session**. A DO owns a Pi Durable conversation; nothing else may drive the same conversation concurrently.

#### Pi Durable: actual recovery boundary

[`src/harness/tool.ts`, approximately lines 150–230](https://github.com/earendil-works/pi/blob/f09d01b85e0384647fcab6779d35ab9dabe04be3/packages/durable/src/harness/tool.ts#L150-L230): the prepare phase validates arguments, runs `beforeTool`, and commits an execute checkpoint containing the final arguments and replay policy before executing. On recovery, execution reruns only when both the stored and current tool definition say `replay: "safe"`. Otherwise the model receives an interrupted result that explicitly says the tool may have partially run.

Consequences:

- Durable agent state is not exactly-once shell execution.
- Never mark arbitrary shell commands safe just to make recovery automatic.
- A remote job needs a persisted identity and reconciliation, not simply another POST after an exception.
- A basic `ExecutionEnv` is a filesystem/command interface, not automatically a durable job protocol. For task-aware reconciliation, a custom shell tool can use `api.taskId`, commits, and runner operation records.

[`test/examples/22-subagent-background.ts`](https://github.com/earendil-works/pi/blob/f09d01b85e0384647fcab6779d35ab9dabe04be3/packages/durable/test/examples/22-subagent-background.ts): named child conversations have durable anchor tasks; reporter tasks submit a message, await its answer, and report back to the parent. Request IDs prevent repeated admission/reporting across restarts. The tool exposes spawn, send, stop, and status. This is executable example/product code to adapt, not an installed universal agent bus.

[`test/examples/28-sandbox-per-conversation.ts`](https://github.com/earendil-works/pi/blob/f09d01b85e0384647fcab6779d35ab9dabe04be3/packages/durable/test/examples/28-sandbox-per-conversation.ts): workspace assignment is application state in a document. The environment factory reads that assignment for each conversation. Sandbox lifecycle ownership belongs in the application, not in model-provider selection.

[`src/harness/view.ts`](https://github.com/earendil-works/pi/blob/f09d01b85e0384647fcab6779d35ab9dabe04be3/packages/durable/src/harness/view.ts) and [README: watching a conversation](https://github.com/earendil-works/pi/tree/f09d01b85e0384647fcab6779d35ab9dabe04be3/packages/durable#watching-a-conversation): a client receives current state and subsequent changes. Reconnection is not guaranteed replay of every token event. Streamed progress can use deferred persistence; default settings permit roughly the newest second of partial output to be lost on a crash. Final entries/task transitions have stronger commit semantics.

#### Cloudflare PiHarness: keep the host integration

[`packages/agents/src/harness/pi/harness.ts`](https://github.com/cloudflare/agents/blob/be1749221ab3efc8be4e976d8e7d8344d1446032/packages/agents/src/harness/pi/harness.ts): PiHarness is library code under `agents/harness/pi`, not just the example's websocket handler. It prepares storage, opens the application's Harness factory, and manages a Lifecycle wake job. It schedules wake work before admitting input and passes the caller's operation ID to Pi as `requestId`.

The host's heartbeat is 30 seconds and each wake waits at most ten minutes before handing off to another alarm. The comments account for the platform's fifteen-minute alarm wall-time boundary. Pass `onWake` through to `Harness.open`: sleeping durable tasks can then release the object rather than being kept alive by ordinary timers. This does not make a single indefinitely streaming provider request immune to platform limits.

The example uses an SQLite-backed Cloudflare Computer filesystem and Dynamic Worker JavaScript execution. That is not a Linux workspace with Docker. Reuse the lifecycle pattern; replace its workspace/tool integration with the sandbox provider. Its generated session IDs and permissive example routing are not production authentication or ownership checks.

### Recommended topology

```text
Future native clients / CLI; MCP later
                  |
              HTTP + SSE
                  |
Cloudflare Worker / Hono
  authentication, validation, ownership, limits
                  |
Thread Durable Object / application session controller
  admission IDs, workspace reference
  approval records, execution reconciliation, UI projection
                  |
PiHarness + Pi Durable
  DO SQLite transcript/tasks
  Pi AI -> API-key providers
                  |
         sandbox tools / command jobs
                  |
         E2B sandbox (one per session)
           repo/worktrees, Docker
```

For a Pi-only subagent tree, keep child conversations in the parent's Harness/DO initially so ownership, reporter tasks, and commits remain local to it. A separate top-level thread can have its own DO. Cross-DO messaging is an explicit external delivery boundary.

#### State ownership

| State                                           | Authority                                                        |
| ----------------------------------------------- | ---------------------------------------------------------------- |
| Account/thread discovery                        | Account-level index; cached metadata, not an extra model runtime |
| Pi transcript, submissions, tool tasks, retries | Pi Durable in DO SQLite                                          |
| Workspace lifecycle and assignment              | Application controller reconciled against the provider's state   |
| Files, worktrees, databases, Docker data        | The session's sandbox                                            |
| Large logs, attachments, transcript backups     | R2 when necessary; not a competing live conversation store       |

Keep application thread IDs, engine session IDs, sandbox IDs and operation IDs distinct.

### Native UI

Normalize the common surface: session metadata and capabilities, messages/content blocks, tool activity, run status, approval/question requests, and subagent relationships. Preserve raw engine payloads/version metadata for unsupported details and diagnostics. Do not reduce everything to `text` and `busy`, and do not promise that arbitrary TUI widgets can be rendered natively.

Pi Durable has its own API and storage. Pi coding-agent SDK/RPC uses `AgentSession` and `SessionManager`. They share model infrastructure but are not the same runtime or interchangeable live session format, so CLI extensions do not drop into Durable.

### Command recovery policy

1. Persist the logical operation ID and intent before dispatch.
2. Record the returned process/runner job identity and output offsets.
3. Reconnect to the same job after control-plane loss; do not launch again just because the HTTP request was retried.
4. If dispatch may have happened but no job ID was durably recorded, reconcile using a runner-owned logical ID where supported. Otherwise surface an uncertain outcome rather than blindly repeating an unsafe command.
5. Bound IDs by workspace and runner boot/generation so a reused PID cannot identify an old operation.
6. Drain/checkpoint agent activity before a deliberate stop, or explicitly mark affected runs interrupted and reconcile on resume.

The remote implementation labels runs for some transport-failure reconciliation; that is not a blanket deduplication guarantee for arbitrary callers and retries.

### Agent-to-agent communication

Use engine-native durable primitives within Pi's Harness, and a small application-level delivery interface across Durable Object boundaries:

- Start/delegate a task with an explicit owner and workspace/worktree policy.
- Send a message with a stable logical delivery ID and requested steer/follow-up behavior.
- Observe/wait for completion; deliver a result through a reporter/outbox mechanism.
- Cancel with explicit foreground/background ownership semantics.

Use one worktree per concurrently editing agent by default. A shared VM is not permission isolation, and separate model conversations do not prevent concurrent file edits or Git index conflicts.

### Server-first API scope

Keep the first public surface small:

- Create/list/get sessions; bind each to its workspace.
- Submit a message with caller operation ID; receipt means admission, not completion.
- Fetch a current snapshot and paginated history.
- Stream native-UI events over SSE, including authoritative snapshot/reset on reconnect.
- Interrupt/cancel supported work and answer a specific approval/question.
- Observe/start/stop/resume the assigned workspace where required.

For event transport, use an application-owned cursor/epoch where replay is promised, or explicitly resnapshot. Pi's committed transcript can remain authoritative instead of duplicating it wholesale in another transcript database.

Persist approval records bound to engine session, run/generation, tool-call ID, and arguments. In Pi Durable, `beforeTool` returning `block` is a failed tool result, not automatically a durable pending-approval queue. Long approval waits must be implemented with durable task/state transitions, not merely a Promise retained in memory.

### Build order

1. **One Pi vertical slice.** Authenticated Hono API, Thread DO/PiHarness, one server-provisioned sandbox per session ([Workspaces](#workspaces)), Anthropic API key ([Model authentication](#model-authentication)), file/shell tools, snapshot/SSE, explicit cancellation. First verify unknown remote command outcomes and lost-receipt retries. No custom Computer filesystem layer is needed when the sandbox is the filesystem.
2. **Durable delegation.** Adapt the Pi background-subagent example. Reuse ownership/reporters rather than creating a second generic scheduler.
3. **Clients and MCP later.** Test server contracts with scripts/HTTP clients now. Implement native iOS against the same snapshot/event/approval contract later. Add MCP as another API adapter, not a second orchestration engine.

### Alternative: VM-centered runtime

If full Pi CLI extensions and identical CLI behavior outrank DO-owned durability, put the session host in the sandbox and use Pi coding-agent SDK/RPC there. The DO then holds control-plane receipts/projections rather than a PiHarness driving those sessions. Pi Durable could also run under Node with SQLite in the sandbox if durable checkpoints are desired, but it remains a distinct runtime from Pi coding-agent.

This reduces the split between tools and model execution but makes availability and transcript durability depend on the runner, VM lifecycle, and backups. It is a valid alternative, not something to combine with a second active DO model loop for the same session. For the durable-cloud design and native UI goal, retain Worker-hosted Pi.

### Validation gates before calling the server reliable

- Drop the client immediately after admission; retry with the same operation ID and observe one admitted input.
- Crash the DO during a remote command, including after remote launch but before saving its handle; prove no blind re-execution.
- Reconnect snapshot/SSE during a tool call, compaction, and pending approval.
- Pause and resume an E2B sandbox; demonstrate which files and processes remain, and safe reconciliation.
- Edit concurrently in two agent worktrees; verify no unintended shared Git index or credential/template leakage.

No code was changed in the reference checkouts, no live VM was provisioned, and no paid model call or upstream test suite was run during this evaluation. That limit matters most for command crash windows.
