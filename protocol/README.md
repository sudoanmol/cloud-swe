# First slice: cloud Pi in a sandbox

The route table is the frozen contract. A route with a slice in its Built column is designed but not built yet; the slices are those of the iOS handoff, and until each lands the server answers as its note says. These are application contracts, not native Pi wire types. See [source verification](SOURCE-VERIFICATION.md) and [server status/testing](../server/README.md). Import runtime schemas and inferred types from `@cloud-swe/protocol`. This private workspace package exports TypeScript source for bundler-based clients/backends; it has no Node-only runtime dependencies.

## Shipping target

A personal authenticated Hono API owns one Pi session through a Thread Durable Object/PiHarness, using its own server-provisioned sandbox on E2B for read/write/shell tools ([design](../docs/architecture.md#workspaces)). Pi Durable owns the transcript. No second agent loop in the sandbox. Public workspace endpoints, Claude, Mac, delegation, UI, and MCP are out of this slice.

Before runtime work, configure an allowlist of sandbox templates (E2B template names) and a server-side model allowlist. Requests select those references, never supply provider credentials or arbitrary runner URLs. File/shell access is privileged personal access, not a multi-tenant sandbox.

## HTTP surface

Every route except sign-in requires `Authorization: Bearer <session token>` over HTTPS. This is the Better Auth session token, not a model-provider or Claude subscription token. A browser gets it from `GET /v1/auth/login`, which ends on `GET /v1/auth/token`. The app (S2) uses RFC 8252 with PKCE: it opens `GET /v1/auth/login?redirect_uri=…&code_challenge=…&code_challenge_method=S256` in the system's sign-in sheet, the server redirects to `APP_REDIRECT_URI?code=<code>` (`com.anmolhurkat.cloudswe:/sign-in`, the only redirect it accepts, else 400 `invalid_redirect`), and the app sends `{ code, codeVerifier }` to `POST /v1/auth/exchange` for the token. A code works once, within `SIGN_IN_CODE_TTL_SECONDS` (60); any bad, used or expired code, or a wrong verifier, is 400 `invalid_sign_in_code`. Only the GitHub account in `GITHUB_ALLOWED_USER_ID` can get one. Authenticate and check ownership before session/operation lookup; inaccessible IDs return 404. No credentials in URLs or SSE payloads.

Conversation routes sit under `/v1/sessions/:sessionId/conversations/:conversationId` (`ConversationParams`), written `…/c/:conversationId` below. The active one is `Session.activeConversationId`.

JSON mutation bodies are strict. Reject oversized bodies before parsing (128 KiB ceiling); reject invalid schema input with 400, missing/invalid authentication with 401, missing resources with 404, conflicting operations, inactive runs and busy sessions with 409 (`session_busy`, `session_settling`, `input_queue_full`, `sandbox_limit_reached` when MAX_SANDBOXES are running), unavailable dependencies with 503, and unexpected failures with 500. All JSON errors use `ApiError`; `ApiErrorCode` lists every code and `server/src/errors.ts` owns each code's status and person-readable message. Messages never carry raw exceptions, secrets or upstream text. Validate outbound responses too.

## Admission and recovery rules

- The client generates a UUID operation ID **before** sending, and reuses it on retries. Scope session creation IDs to the authenticated owner; scope message/cancel IDs to owner + session. Retain creation mappings and accepted receipts for the session lifetime; do not expire them while a session remains usable.
- Same operation ID + same parsed intent returns the original result. Same ID + different action/payload returns `operation_conflict` (409). Check deduplication before busy/run checks. Creation retries return the same session ID and current session metadata. A creation retry must repeat the body as first sent: `CreateSessionRequest.template` and `.model` are optional (the server uses the first allowed template and its configured model), and a retry that names a default the first request left out, or leaves out one it named, is a different body.
- `Session` is frozen: `id`, `title`, `activeConversationId`, `model` (`{ provider, id }`), `workspace` (`{ id, state }`), `environment`, `run`, `compaction`, `compactionFailure`, `pending`, `repos`, `approvals`, `pullRequests`, `questions`, `secretRequests`, `todos`, `usage`, `createdAt`, `updatedAt`. `run`, `compaction`, `compactionFailure`, `pending` and `todos` describe the active conversation. `usage` is Pi's token and cost record summed over every conversation, cost in US dollars at the catalog price (zeros until S4). Adding a field is a protocol change; nothing engine- or provider-internal appears in it. `title` is null until the first user message is admitted, then that message's first line, trimmed and cut to `SESSION_TITLE_LIMIT` (80) characters (`sessionTitle`); `PATCH /v1/sessions/:sessionId` with `{ title }` renames it, and a rename stays. A message without a configured model key is refused with 503 `model_unavailable`.
- Persist intent before dispatch; use the logical ID as Pi's admission request ID and reconcile on recovery. An HTTP timeout is not rejection. Operation lookup returns a receipt only after confirmed admission; unresolved admission returns 503, not an invented success. Retry the original mutation with the same ID, never a new ID to escape uncertainty.
- A receipt means admission, **not completion**. Messages default to `mode: "reject"`; `"steer"` is delivered at Pi's next boundary, and `"followUp"` queues behind the current generation. Steering does not interrupt an in-flight model request and starts normally if idle. Follow-ups are FIFO, at most one per final boundary; Pi can consume pending steers at that same boundary. At most 100 native inputs may be pending. `Session.pending` lists their receipts/modes and native queued/running/parked status. This is a projection, not another scheduler.
- `Session.compaction` is Pi's live compaction (reason, blocking, attempt, `nextAttemptAt` while backing off) and `Session.compactionFailure` its newest failure; both carry fixed safe messages and ride in snapshot/SSE frames.
- `Session.questions` lists open questions from `ask_user_question` plus the 20 most recent answered ones, which drop their option previews. At most 80 can be open; past that the tool tells the agent to wait for answers. The tool returns at once, and the agent keeps working until it needs the answer. The answer arrives as a steering message: it joins running work at the next boundary, or starts a run if the agent has stopped. An answer names every question once by `optionIndexes` and/or `text`, with optional `notes` per question and an optional `globalNote`; or the request is `{ "decline": true }`. Anything else is a 400 and changes nothing. A repeat returns the first answer with 200 and starts nothing. If the message can't be admitted, the route still returns the answer: it stays saved, and a durable job in the Thread retries delivery every 15 s until admitted, with no client retry. A new message leaves an open question open.
- **Environments** (`@cloud-swe/protocol/environments`) are named account-level sets of secrets, chosen per session with `CreateSessionRequest.environment` and projected as `Session.environment` (`null` is the empty default). A variable (normal secret) is visible to the client and the agent and enters the sandbox as an env var. A network secret is write-only: no response returns its value or placeholder, and `EnvironmentView` can't carry either. A name is one kind or the other (409 `secret_name_conflict`). Limits are `ENVIRONMENT_LIMITS`: 20 environments, 50 variables and 20 network secrets each (409 `environment_limit`), 1 to 10 hosts per network secret. A host must be a lowercase DNS name, never an IP, port, wildcard, localhost, GitHub, a package registry in `EXCLUDED_HOSTS` or the Worker's own host (400 `invalid_host`). Creation checks that the environment exists (400 `unknown_environment`); a retry or a replacement sandbox doesn't. A deleted environment reads as empty, and recreating the name reconnects its old sessions. Network secrets are transparent to code in the sandbox: it holds a placeholder, and an egress daemon sends requests for approved hosts through the Worker, which swaps in the value ([wire contract](../server/README.md#network-secrets)). Approved hosts must be trusted: one that echoes request headers returns the key. Environment changes don't push over SSE; re-read `GET /v1/environments`.
- `Session.secretRequests` lists open `request_network_secret` requests plus the 20 most recent decided ones: the name, the hosts the agent asked for, the header and its reason, never a value. The client shows the hosts plainly and the user confirms or edits them, since an injected agent could ask for a key with a hostile host. An answer is `{ "value", "hosts" }` or `{ "decline": true }`. The value goes straight into the session's environment as a network secret and never into the Thread; only the outcome, by name and hosts, reaches the agent as a steering message, delivered durably like a question's answer. A session without an environment can't file one (the tool says `no_environment`).
- `Session.todos` is the agent's current task list from the `todo` tool, without deleted tasks.
- Every input gets its own app receipt/run ID, not a Pi task ID: multiple inputs can share a native generation. `Session.run` shows the oldest running input (or first queued input while starting); with no pending input it shows the last admitted input's outcome. Cancellation names one pending app run ID and resolves it to the saved native operation. A queued input is withdrawn without interrupting the active generation; a placed input captures the current pending-input scope **including queued inputs** for cancellation. The scope is persisted before dispatch and never expands on retry. Cancellation resolves a placed input to its bound native task in a Pi transaction and aborts that task, not whichever conversation/task happens to be current later. Delayed/stale cancellations never target a newer input. `cancelling` is not `cancelled`; interruption must be confirmed. Cancellation intents and accepted receipts survive retry/restart. Cancellation returns a `CancelRunResponse`: the receipt plus `restoredMessages` (operation ID, mode, text) for queued inputs removed from the inbox. The client restores these drafts to its editor, matching Pi interactive Escape. Server-written inputs (an approval result or a question answer) are never restored: their text is kept as a model-only notice in the conversation, so the next run sees it and none starts for it. Direct Pi `AgentSession.abort()` does not itself clear queues; Escape's UI handler clears/restores them before aborting.
- `CommandRecord` is internal persisted execution state. Save `prepared` before dispatch. Workspace + operation UUID identifies intent; a PID alone is insufficient. Reconcile to the existing job after lost receipts, and never re-execute automatically. `uncertain` means the remote state cannot currently be read. A reachable command that stops reporting becomes terminal `lost`: a cancel marker is written first, so it cannot start late, but anything it already began may have happened. Null/missing exit codes are not success. Apply the same caution to remote writes.
- An uncertain remote effect blocks new mutating work until reconciled. Cancellation resolves it to a terminal state once the sandbox is reachable, and stays unresolved (503, retryable) until then. No exactly-once shell guarantee is claimed.
- Reads never touch the sandbox: get, list, snapshot, history and events only project stored state, plus `workspace.state`, which the catalog reads from the provider's control plane (cached for 15 s) so a stopped or deleted sandbox is visible. A command Pi no longer owns (an orphan) is stopped by a durable Lifecycle job in the Thread, retried every 5 seconds while any command is open and surviving a restart. Message submission also waits up to 10 seconds for orphans to stop before admission, so a resolvable orphan never causes `busy`; one that is still unresolved after that does.
- `Session.updatedAt` is the time of the newest committed transcript message of the active conversation, or of the last rewind if that is later, or `createdAt` before either. It is derived on read, never written per event.
- The list returns `SessionSummary` rows (`sessionSummary()` builds one from a `Session`): title, `preview` (start of the newest message, up to `SESSION_PREVIEW_LIMIT`), `run`, `openRequests` (pending approvals, questions and secret requests), `activeConversationId`, `createdAt`, `updatedAt`, newest `updatedAt` first. S7 serves them from summary rows in the Catalog, so the list never wakes a session; until then the server asks each session, leaves out one it can't read, keeps creation order and sends a null preview.
- **Conversations.** `ConversationId` is Pi's conversation ID as an opaque string, stable within its session. Messages, cancel, compact, snapshot, events and history are per conversation; a client keys its cached transcript by session and conversation. A conversation that isn't in the session is 404 `conversation_not_found`; a message, cancel or compaction to one the session has moved off is 409 `conversation_not_active`. `OperationReceipt` and `Snapshot` name their conversation, and a history cursor works only in the conversation that issued it.
- **Going back (rewind).** `POST …/c/:conversationId/rewind` with `{ operationId, before }` removes the entry `before` names and every entry after it from the session's conversation, which continues from just above it. Editing a message is a rewind before that message, then a normal message with the new text. Pi's transcript only grows, so the server forks: the entries above the cut are shared with a new conversation, which becomes `Session.activeConversationId`, and the receipt's `conversationId` names it. The conversation the request named stays readable and takes no more messages (409 `conversation_not_active`), and no route makes it active again. Only the active conversation can be rewound, and only while the session is idle: a run, a queued message, a cancellation in flight, a compaction, an unresolved command, an approval being carried out on GitHub, a secret being saved or a request's outcome on its way to the agent is 409 `session_not_idle` (cancel or wait first). A request that only waits on the user does not make the session busy. `before` must be an entry of the conversation (404 `entry_not_found`); the first entry gives an empty conversation. A retry with the same `operationId` returns the first receipt and cuts nothing more; the ID of a message or cancellation, or the same ID with another conversation or entry, is 409 `operation_conflict`. The receipt comes back only from the call or its retry, not from `GET …/operations/:operationId`. A rewind never changes files or Git in the sandbox. When the agent ran a tool that can change files in the cut part (`bash`, `write`, `edit`, `codemode`, `git_clone`), the new conversation gets a model-only notice saying files were not reverted; clients see it as a `native` entry without its text. Approvals, questions and secret requests filed in the cut part are removed and nothing about them reaches the agent; one already decided there is kept, without its result message. Those filed above the cut stay. A session whose `activeConversationId` is not `"1"` has been rewound at least once.
- **Images** (`@cloud-swe/protocol/attachments`). The client names an image with a UUID and `PUT`s two files under it, each raw bytes with an image `Content-Type` (PNG, JPEG, GIF or WebP; another type is 415 `attachment_type_unsupported`): the model copy, which a message needs and the model sees, and optionally the original, which only the client fetches back. The app makes both; the server never resizes. Limits are `ATTACHMENT_LIMITS`: a model copy at most 5 MiB and `modelEdge` (2,576) pixels on its longer side, an original at most 20 MiB (413 `attachment_too_large`), 5 images per message. A model copy whose header is not an image of its type is 415, and one too many pixels wide or tall is 422 `attachment_dimensions_too_large`. A retry with the same bytes is the same upload; other bytes or another type under the ID are 409 `operation_conflict`. `SubmitMessageRequest.attachments` names them, after the still-required text; an unknown one, or one without its model copy, is 404 `attachment_not_found`. Transcript entries show `{ kind: 'image', attachmentId, mediaType }`, and `Session.pending` and `restoredMessages` carry `attachments` back. The model fetches each model copy from a public bucket by an unguessable address that no API returns. An image a message has named is kept for the session's life; of those no message has named, the session keeps the newest 20, and an older one is removed and must be uploaded again.

## Snapshot, history, and SSE

- A `Snapshot` is a conversation for a client that holds none of it: `conversationId`, `session`, `history` (the newest committed entries, at most 100, with a cursor to older ones) and `live` (`LiveState`: the streaming assistant message, or null, and the running tools, at most 100, with `toolsTruncated`). The streaming message is never an entry: it becomes one when Pi commits it. History pages go backwards using opaque cursors bound to the session and conversation; each page's entries are ordered oldest to newest. Clients prepend older pages and deduplicate by entry ID. Session-list cursors are opaque too. Invalid or wrong-scope cursors return 400 `invalid_cursor`. Snapshot and SSE entries omit the raw `native` record, which only paginated history returns.
- The stream's rules are written on `SessionEvent` and are the contract: `snapshot` replaces everything live (on connect without a usable cursor, and on any reset); `session` replaces the session and is the 15-second heartbeat; `entries` replaces or appends committed entries by ID, with `after` to spot a gap; `live` replaces the live layer and comes at most about every 100 ms. The SSE `id:` is the newest committed entry; a reconnect sends `Last-Event-ID` or `?after=` (`EventsQuery`; the header wins) and continues with `session`, `entries` and `live` when that entry is in the conversation and at most 100 behind, otherwise from a `snapshot`. `event:` is the kind. Within one frame the events come as `entries`, `live`, `session`, so a run never shows as ended before its last entry.
- Atomically capture the snapshot and subscribe to subsequent changes so there is no snapshot-to-stream gap. After headers are sent, transport failure closes the stream; it cannot become a JSON error response.
- **Clients stay in sync.** Every client on a session gets the same state on its own stream: messages (queued ones through `Session.pending`, with their text), run state, tool activity and approvals. Workspace state can lag by up to one heartbeat.
- Streaming text is provisional; committed transcript entries remain authoritative after restart. No parallel application transcript database. `unreachable` is not `stopped` or `idle`.

### What a client does with the stream

The same rules the server tests apply in `server/test/event-stream.ts`, where applying every event to the first snapshot must give exactly what `GET .../snapshot` returns.

1. Keep the session, the conversation's committed entries in order, `history.nextCursor`, the live layer, and `lastId`: the last SSE `id:` received (empty means none).
2. After applying an event that has an `id:` line, set `lastId` to it. An event without one leaves it unchanged.
3. `snapshot`: replace the session, the committed tail, `nextCursor` and the live layer. Keep older pages fetched from history, by entry ID. It can come at any time, not only first.
4. `session`: replace the session. One arrives at least every 15 seconds; after about 30 seconds without any event, treat the connection as dead and reconnect.
5. `entries`: first check that `after` equals `lastId` (null equals empty). If it does not, entries were missed: close and reconnect with `lastId`. Otherwise replace each entry whose ID is already held, and append the rest. An old ID can come again: a tool entry whose outcome changed.
6. A committed tool entry with outcome `uncertain` is provisional. A client holding one when it reconnects does so without a cursor and takes the snapshot, because the server cannot tell whether it resolved meanwhile.
7. `live`: replace the live layer whole.
8. Reconnect with `Last-Event-ID: <lastId>`, or `?after=<lastId>` when opening fresh from a cached transcript. Expect either a `snapshot`, or `session`, then `entries` if any, then `live`.
9. Older pages: page `history` from the snapshot's `nextCursor`. It stays right as entries are appended, because it points before the first held entry.
10. After applying a `session` or `snapshot` event, compare `session.activeConversationId` with the stream's conversation. If they differ, the session was rewound: its `run`, `pending` and `todos` now describe the new conversation. Close the stream and open the active conversation's, either without a cursor (a `snapshot` follows) or with `?after=<the newest held entry above the cut>` after dropping the held entries from the cut on, which continues without a snapshot.

## Tolerance and fixtures

An older client must read a newer server, so every enum and tagged union in a response is open: a newer server may add a value or variant, and a client keeps an unknown enum value as its raw string and decodes an unknown variant as unknown. Response fields are only added. Request enums are closed. `protocol/fixtures/` holds one JSON sample per response, event kind and union variant, exactly as the schemas produce it; the Swift client's tests decode every file. `protocol/test/fixtures.test.ts` fails when a file differs from what the schemas produce or a union gains a variant without one; `pnpm --filter @cloud-swe/protocol fixtures` rewrites them.

## Acceptance gate for the later implementation

1. Auth/ownership rejection and all responses validated against this package.
2. Lost create/message receipt + same-ID retry admits one session/input; changed intent returns 409.
3. One prompt reads/writes a file and runs a shell command in the session's sandbox.
4. Disconnect/reconnect during tool execution produces a consistent snapshot and later updates.
5. Cancel a specific run; a stale cancel cannot affect its successor.
6. Crash before/after remote launch and before saving its handle: reconnect to the same job or surface uncertainty, never blind replay.

Run `pnpm test` from the repository root: contract tests, typechecks and session-creation integration tests all execute inside Docker. `pnpm test --e2b` also runs the E2B tests on real, billed sandboxes. Creation and message admission/retry/restart behavior are tested. Model transport is intercepted, with no paid model calls. Steering, FIFO follow-ups, queued/active cancellation, stale-cancel rejection and restart receipts are tested. Snapshot, pagination, disconnect/reconnect and restart behavior are tested with native Pi. Tool/compaction fault-injection gates above remain future work.
