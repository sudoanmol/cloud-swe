# First slice: cloud Pi in a sandbox

Every route in the table below is implemented; schemas not used by a route describe later endpoints. These are application contracts, not native Pi wire types. See [source verification](SOURCE-VERIFICATION.md) and [server status/testing](../server/README.md). Import runtime schemas and inferred types from `@cloud-swe/protocol`. This private workspace package exports TypeScript source for bundler-based clients/backends; it has no Node-only runtime dependencies.

## Shipping target

A personal authenticated Hono API owns one Pi session through a Thread Durable Object/PiHarness, using its own server-provisioned sandbox on E2B for read/write/shell tools ([design](../docs/architecture.md#workspaces)). Pi Durable owns the transcript. No second agent loop in the sandbox. Public workspace endpoints, Claude, Mac, delegation, UI, and MCP are out of this slice.

Before runtime work, configure an allowlist of sandbox templates (E2B template names) and a server-side model allowlist. Requests select those references, never supply provider credentials or arbitrary runner URLs. File/shell access is privileged personal access, not a multi-tenant sandbox.

## HTTP surface

Every route except sign-in requires `Authorization: Bearer <session token>` over HTTPS. This is the Better Auth session token from `GET /v1/auth/token`, not a model-provider or Claude subscription token. Only the GitHub account in `GITHUB_ALLOWED_USER_ID` can get one. Authenticate and check ownership before session/operation lookup; inaccessible IDs return 404. No credentials in URLs or SSE payloads.

| Method | Path                                              | Input                   | Success schema/status                          |
| ------ | ------------------------------------------------- | ----------------------- | ---------------------------------------------- |
| POST   | `/v1/sessions`                                    | `CreateSessionRequest`  | `CreateSessionResponse`, 201 (200 on retry)    |
| GET    | `/v1/sessions`                                    | `PageQuery`             | `ListSessionsResponse`, 200                    |
| GET    | `/v1/sessions/:sessionId`                         | `SessionParams`         | `Session`, 200                                 |
| POST   | `/v1/sessions/:sessionId/messages`                | `SubmitMessageRequest`  | `OperationReceipt`, 202                        |
| POST   | `/v1/sessions/:sessionId/compact`                 | `CompactRequest`        | empty, 202 (409 `compaction_running`)          |
| POST   | `/v1/sessions/:sessionId/cancel`                  | `CancelRunRequest`      | `OperationReceipt`, 202                        |
| GET    | `/v1/sessions/:sessionId/operations/:operationId` | `OperationParams`       | `OperationReceipt`, 200                        |
| GET    | `/v1/sessions/:sessionId/snapshot`                | `SessionParams`         | `Snapshot`, 200                                |
| GET    | `/v1/sessions/:sessionId/history`                 | `PageQuery`             | `HistoryResponse`, 200                         |
| GET    | `/v1/sessions/:sessionId/events`                  | `SessionParams`         | SSE containing `SessionEvent`, 200             |
| POST   | `/v1/sessions/:sessionId/approvals/:approvalId`   | `DecideApprovalRequest` | `Approval`, 200 (409 on the opposite decision) |
| POST   | `/v1/sessions/:sessionId/questions/:questionId`   | `AnswerQuestionRequest` | `Question`, 200 (first answer wins)            |
| GET    | `/v1/auth/token`                                  | signed-in session       | `AuthToken`, 200 (no-store)                    |

JSON mutation bodies are strict. Reject oversized bodies before parsing (128 KiB ceiling); reject invalid schema input with 400, missing/invalid authentication with 401, missing resources with 404, conflicting operations, inactive runs and busy sessions with 409 (`session_busy`, `session_settling`, `input_queue_full`, `sandbox_limit_reached` when MAX_SANDBOXES are running), unavailable dependencies with 503, and unexpected failures with 500. All JSON errors use `ApiError`; `ApiErrorCode` lists every code and `server/src/errors.ts` owns each code's status and person-readable message. Messages never carry raw exceptions, secrets or upstream text. Validate outbound responses too.

## Admission and recovery rules

- The client generates a UUID operation ID **before** sending, and reuses it on retries. Scope session creation IDs to the authenticated owner; scope message/cancel IDs to owner + session. Retain creation mappings and accepted receipts for the session lifetime; do not expire them while a session remains usable.
- Same operation ID + same parsed intent returns the original result. Same ID + different action/payload returns `operation_conflict` (409). Check deduplication before busy/run checks. Creation retries return the same session ID and current session metadata.
- Persist intent before dispatch; use the logical ID as Pi's admission request ID and reconcile on recovery. An HTTP timeout is not rejection. Operation lookup returns a receipt only after confirmed admission; unresolved admission returns 503, not an invented success. Retry the original mutation with the same ID, never a new ID to escape uncertainty.
- A receipt means admission, **not completion**. Messages default to `mode: "reject"`; `"steer"` is delivered at Pi's next boundary, and `"followUp"` queues behind the current generation. Steering does not interrupt an in-flight model request and starts normally if idle. Follow-ups are FIFO, at most one per final boundary; Pi can consume pending steers at that same boundary. At most 100 native inputs may be pending. `Session.pending` lists their receipts/modes and native queued/running/parked status. This is a projection, not another scheduler.
- `Session.compaction` is Pi's live compaction (reason, blocking, attempt, `nextAttemptAt` while backing off) and `Session.compactionFailure` its newest failure; both carry fixed safe messages and ride in snapshot/SSE frames.
- `Session.questions` lists open questions from `ask_user_question` plus the 20 most recent answered ones, which drop their option previews. At most 80 can be open; past that the tool tells the agent to wait for answers. The tool returns at once, and the agent keeps working until it needs the answer. The answer arrives as a steering message: it joins running work at the next boundary, or starts a run if the agent has stopped. An answer names every question once by `optionIndexes` and/or `text`, with optional `notes` per question and an optional `globalNote`; or the request is `{ "decline": true }`. Anything else is a 400 and changes nothing. A repeat returns the first answer with 200 and starts nothing. If the message can't be admitted, the route still returns the answer: it stays saved, and a durable job in the Thread retries delivery every 15 s until admitted, with no client retry. A new message leaves an open question open.
- `Session.todos` is the agent's current task list from the `todo` tool, without deleted tasks.
- Every input gets its own app receipt/run ID, not a Pi task ID: multiple inputs can share a native generation. `Session.run` shows the oldest running input (or first queued input while starting); with no pending input it shows the last admitted input's outcome. Cancellation names one pending app run ID and resolves it to the saved native operation. A queued input is withdrawn without interrupting the active generation; a placed input captures the current pending-input scope **including queued inputs** for cancellation. The scope is persisted before dispatch and never expands on retry. Cancellation resolves a placed input to its bound native task in a Pi transaction and aborts that task, not whichever conversation/task happens to be current later. Delayed/stale cancellations never target a newer input. `cancelling` is not `cancelled`; interruption must be confirmed. Cancellation intents and accepted receipts survive retry/restart. Cancellation returns a `CancelRunResponse`: the receipt plus `restoredMessages` (operation ID, mode, text) for queued inputs removed from the inbox. The client restores these drafts to its editor, matching Pi interactive Escape. Server-written inputs (an approval result or a question answer) are never restored: their text is kept as a model-only notice in the conversation, so the next run sees it and none starts for it. Direct Pi `AgentSession.abort()` does not itself clear queues; Escape's UI handler clears/restores them before aborting.
- `CommandRecord` is internal persisted execution state. Save `prepared` before dispatch. Workspace + operation UUID identifies intent; a PID alone is insufficient. Reconcile to the existing job after lost receipts, and never re-execute automatically. `uncertain` means the remote state cannot currently be read. A reachable command that stops reporting becomes terminal `lost`: a cancel marker is written first, so it cannot start late, but anything it already began may have happened. Null/missing exit codes are not success. Apply the same caution to remote writes.
- An uncertain remote effect blocks new mutating work until reconciled. Cancellation resolves it to a terminal state once the sandbox is reachable, and stays unresolved (503, retryable) until then. No exactly-once shell guarantee is claimed.
- Reads never touch the sandbox: get, list, snapshot, history and events only project stored state, plus `workspace.state`, which the catalog reads from the provider's control plane (cached for 15 s) so a stopped or deleted sandbox is visible. A command Pi no longer owns (an orphan) is stopped by a durable Lifecycle job in the Thread, retried every 5 seconds while any command is open and surviving a restart. Message submission also waits up to 10 seconds for orphans to stop before admission, so a resolvable orphan never causes `busy`; one that is still unresolved after that does.
- `Session.updatedAt` is the time of the newest committed transcript message, or `createdAt` before any. It is derived on read, never written per event.
- `ListSessionsResponse.unavailable` names sessions on the page whose Thread could not be read; the rest of the page is still returned, and a retry may succeed.

## Snapshot, history, and SSE

- Snapshot contains current metadata/run state, live tool activity (`tools`, at most 100, with parent/child IDs and `toolsTruncated`) and up to 99 committed entries from the active context plus one live partial. History includes earlier context boundaries. History pages go backwards using opaque, session-bound cursors; each page's entries are ordered oldest to newest. Clients prepend older pages and deduplicate by entry ID. Session-list cursors use a stable `(createdAt, id)` order. Invalid/wrong-scope cursors return 400.
- Atomically capture the snapshot and subscribe to subsequent changes so there is no snapshot-to-stream gap. Each new SSE connection starts with `snapshot`; replace the client's live projection before applying later events. Older paginated committed history may remain cached by entry ID.
- **Clients stay in sync.** Every client on a session gets the same state on its own stream: messages (queued ones through `Session.pending`, with their text), run state, tool activity and approvals. Workspace state can lag by up to one heartbeat.
- Use `event: snapshot` and JSON `data` matching `SessionEvent`, whose only kind is `snapshot`. Every event replaces the client's live projection, including evolving streaming/tool state; there are no entry deltas. Events are ordered within a connection. The 15-second heartbeat re-sends the current snapshot.
- No SSE `id`, durable event cursor, or token replay guarantee yet. Ignore `Last-Event-ID` and resnapshot on reconnect. This first implementation sends replacement snapshots, not entry deltas: a slow client receives the latest snapshot through a single sliding buffer. The server coalesces publications into at most one frame per ~100 ms window (the final state is always sent), and snapshot/SSE entries omit the raw `native` record, which only paginated history returns. Intermediate snapshots may coalesce; older committed entries remain available through history. After headers are sent, transport failure closes the stream; it cannot become a JSON error response.
- Streaming text is provisional; committed transcript entries remain authoritative after restart. No parallel application transcript database. `unreachable` is not `stopped` or `idle`.

## Acceptance gate for the later implementation

1. Auth/ownership rejection and all responses validated against this package.
2. Lost create/message receipt + same-ID retry admits one session/input; changed intent returns 409.
3. One prompt reads/writes a file and runs a shell command in the session's sandbox.
4. Disconnect/reconnect during tool execution produces a consistent snapshot and later updates.
5. Cancel a specific run; a stale cancel cannot affect its successor.
6. Crash before/after remote launch and before saving its handle: reconnect to the same job or surface uncertainty, never blind replay.

Run `pnpm test` from the repository root: contract tests, typechecks and session-creation integration tests all execute inside Docker. `pnpm test --e2b` also runs the E2B tests on real, billed sandboxes. Creation and message admission/retry/restart behavior are tested. Model transport is intercepted, with no paid model calls. Steering, FIFO follow-ups, queued/active cancellation, stale-cancel rejection and restart receipts are tested. Snapshot, pagination, disconnect/reconnect and restart behavior are tested with native Pi. Tool/compaction fault-injection gates above remain future work.
