# Pi source verification

Verified against local source checkouts and the installed npm package declarations on 2026-10-29:

- Pi / Pi Durable **1.4.0**, commit `f09d01b85e0384647fcab6779d35ab9dabe04be3`.
- Cloudflare Agents / PiHarness **0.32.0**, commit `be1749221ab3efc8be4e976d8e7d8344d1446032`.

The original `protocol/src/index.ts` was an **application-owned proposal**, not a transcription of Pi types. It must not be used as a decoder for native Pi events/transcripts.

## Verified distinctions

| Application contract                                  | Actual upstream shape                                                                                                   | Implemented mapping                                                                                                                                                                                                                                                           |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| UUID `Session.id`                                     | Pi Durable branded numeric `ConversationId`; PiHarness addresses it as a decimal string; root is `"1"`                  | One Thread DO per app UUID. `Session.runtime.conversationId` records the native root ID. `getSession()` reads the actual root/agent again.                                                                                                                                    |
| `{ provider, id }` model selector                     | PiHarness accepts this shape; Pi Durable stores `{ provider, modelId }`                                                 | Explicit conversion in `Thread.initialize()`, inverse conversion from `root.agent()` on reads.                                                                                                                                                                                |
| Proposed `OperationReceipt` with app run ID/timestamp | PiHarness `PiReceipt` is `{ operationId, session, accepted }`; `accepted: false` means duplicate admission              | The app saves intent and app run/receipt identity before dispatch, then calls PiHarness with the operation ID. A receipt is returned only after Pi confirms admission. Retries reconcile the native submission before busy/auth checks.                                       |
| Message/tool/native entries with opaque string IDs    | Native `EntryRecord` IDs are numeric, records immutable; roles/content live in `model`, kind/data preserve Pi semantics | Native numeric IDs stringify within their session; no hash or ID mapping table. Normalized messages retain raw native payloads; unknown entries stay native. Snapshot includes live partials, with `live` reserved for replacement snapshots. Historical run IDs can be null. |
| Proposed `SessionEvent` union                         | `watch()` gives a bounded view + Chord operations; `watchEvents()` supplies native agent-event batches                  | Native exact-frame watch feeds replacement snapshot events; a scoped Effect stream stops the watch/heartbeat on cancellation. One sliding snapshot buffer, no durable replay. Native events are not cast to `SessionEvent`.                                                   |
| Proposed UUID `RunId`                                 | Native runs/tasks use their own numeric IDs and documents                                                               | A UUID run ID belongs to one saved message operation. Current run state is projected from its native submission by request ID; it is never cast to a Pi task ID.                                                                                                              |

Message/steer/follow-up capabilities require configured credentials and a catalog model. Cancellation is available without a model key; tools, approvals and delegation remain disabled. Native `PiHarness.pending()` projects pending inputs, with an app run ID per input even when Pi groups inputs in one generation. Follow-ups use `one-at-a-time` boundary policy.

Cancellation persists its captured input IDs under a short DO gate, then interrupts outside the gate. A Pi transaction resolves each still-placed input to `LiveDoc.run.taskId` only if that input is a member. `abortTask`/`waitForTask` target that task; task handovers are re-resolved, and settled inputs never cause a conversation-wide abort. Pi coding-agent's interactive `restoreQueuedMessagesToEditor({ abort: true })` clears both queues, restores their text, then calls `session.abort()`; `AgentSession.abort()` alone does not clear them. Our `CancelRunResponse.restoredMessages` preserves that editor-restoration contract across retries/restarts. Queued inputs use `abortSubmission`; a placement race re-resolves the bound task. This avoids both the 30-second DO gate deadlock and a late conversation-wide abort hitting a successor. Creating a session does not execute a model request or install working file/shell tools. The persisted model selector is checked against the host's configured selector; Anthropic is explicitly registered, with a read-only adapter to the account Credentials DO (client key first, optional Worker test fallback; explicit deletion disables both) and ambient authentication disabled. Message admission checks both before reserving work; provider failures are sanitized before checkpointing.

## Workspace boundary

Docker stands in for Boat's workspace host, **not** for PiHarness, SQLite, or Cloudflare's runtime. Tests use actual workerd/Miniflare with SQLite DOs inside Docker; a separate non-root Docker service exposes an authenticated writable-workspace readiness probe. No host filesystem or Docker socket is exposed to that service.

Boat mode uses the official `@boatdev/sdk` 1.13.0 npm package (`BoatApi.get`, explicitly configured with platform `fetch` rather than its default Node HTTP/2 transport), backed by the documented [`GET /sandboxes/{sandboxId}`](https://docs.boat.dev/api/reference/sandboxes/get-sandbox.md) endpoint and parses only the consumed subset of its `sandbox.info` envelope. `ready`, `idle`, and `running` mean usable for creation; `degraded` does not. No model-owned Boat agent or paid command dispatch is involved in session creation. Live Boat checks require an explicit flag and credentials.
