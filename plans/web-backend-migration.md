## Approach

### 1. Browser data ownership

```text
Next.js UI + TanStack React Query
  -> Better Auth cookies + Fastify REST
  -> active-thread SSE reader
PostgreSQL events <- attempt-owned Pi writer <- coordinator <- sandbox journal
PostgreSQL outbox -> dispatcher -> Temporal -> runner
```

- Use one stable `QueryClientProvider`. REST data lives in `queryOptions`, `infiniteQueryOptions`, and `useMutation`, not a parallel chat store. Endpoint URLs and request bodies belong directly in query/mutation functions.
- Keep a small browser-safe HTTP/SSE transport in `packages/api/src/client.ts`, reusing its decoder and checked errors. Remove `ThreadClient`, `createThreadClient`, and the incomplete lifecycle reducer once their tests migrate. Do not expand the unused endpoint facade.
- No Next route handlers, backend server actions, proxy rewrites, AI SDK `useChat`, SWR, Redis, or browser-to-sandbox connection. Better Auth's client handles its own auth protocol; React Query handles application endpoints.
- Read `NEXT_PUBLIC_API_URL` explicitly. Requests include cookies; mutations send `X-CSRF-Protection: 1`. JSON alone gets `Content-Type: application/json`; multipart uploads must let the browser set its boundary. Pass query AbortSignals through fetch and parse responses with shared Zod schemas.
- Session-scoped keys cover threads, snapshots, questions, providers, catalogs, onboarding, installations and branches. A separate per-thread query-cache entry holds the event projection and its cursor. UI-only state covers drafts, selected model/repo, expansion, and scroll. Do not persist credentials or transcripts through a Query cache persistence plugin.
- Query errors distinguish 401, missing/foreign thread 404, onboarding/configuration failures, busy/idempotency conflicts, capacity/rate limits and network loss. Retry reads with bounded backoff, not validation/auth failures. Mutations default to no automatic retry; explicit submission retry reuses its exact payload and message ID.
- On sign-out/account change, stop readers, cancel outstanding queries, clear Query and mutation caches, drafts, attachment previews and selections. A late response from the old account must not populate the new account's cache.

- New REST operations: `GET /api/onboarding`, `POST /api/onboarding/complete`, and `GET /api/github/installations?page=...`. Extend existing repository listing with an installation-scoped query, `GET /api/github/repositories?installationId=...&page=...`. Preserve the existing unscoped route for non-UI callers; the product picker always supplies an installation ID.
- `GET /api/onboarding` returns the server-owned completion flag, verified GitHub readiness, install URL and provider readiness, never tokens. A transient GitHub error is a retryable status/error, not false proof that installation disappeared. Keep these reads and provider-setup endpoints available before completion.

### 3. GitHub cookie auth and two-step onboarding

- `/` is session-aware. Signed out: full-screen Vercel Labs-inspired background with only centered `cloud-swe` and Sign in with GitHub. Signed in but not onboarded: redirect to dedicated `/onboarding`. Signed in and onboarded: sidebar and new chat. `/login` becomes a redirect to `/`, not a second login screen.
- Use `better-auth/react` against Fastify. OAuth callback remains `{BETTER_AUTH_URL}/api/auth/callback/github`. Successful login returns to `/` and the session gate decides onboarding versus new chat, as requested.
- One shared route gate covers direct links, client navigation, reloads and browser back/forward. Until completion, no chat, history, settings or other product routes mount, query data or open SSE. Only `/onboarding`, auth callbacks/sign-out and required static assets are available to that signed-in user. Onboarded users visiting `/onboarding` return to `/`. Signed-out protected routes return to the root landing. Do not rely on the button flow alone.
- Before mounting protected product routes, confirm completion through our authenticated onboarding response, not a potentially stale cached cookie alone. A backend unavailable response shows Retry rather than treating the session as anonymous. Gate new Pi compute and uploads with the database completion flag so bypassing the browser gate cannot start work. Check new-run eligibility inside the submission transaction after the existing idempotency lookup, so replaying an accepted envelope still returns its original result after credentials are removed. Preserve repository-free scripted local/test API workflows and already-accepted run recovery; never block cancellation or durable question answers as a consequence of onboarding.
- Declare `onboardingCompleted` as a Better Auth user additional field with `input: false`, default false and returned to the authenticated user. Preserve literal inference through `buildAuthOptions` and `createAuth`; infer the client field without duplicating the auth model.
- Enable Better Auth's signed `session_data` cookie cache with a short TTL, initially 60 seconds. Keep its opaque session-token cookie and database sessions. No manually signed cookie, browser bearer token, JWT plugin, account-token cookie or `document.cookie` onboarding flag.
- Fastify's `authProvider.getSession` explicitly uses `disableCookieCache: true` for API authorization. Cookie caching is a UI optimization, not permission to accept revoked sessions or stale onboarding eligibility. Preserve secure HttpOnly attributes and exact trusted origins.
- Initial auth loading shows a shell, not a flash of authenticated content. Unknown/false onboarding state loads server readiness before redirecting. Existing users start false but their installed repositories and saved providers prefill the steps, so no reinstall/re-entry is needed.
- Step 1 shows Install GitHub App, installation status, retry, and the requirement to grant at least one repository. Add server-only `GITHUB_APP_SLUG` configuration to construct the install URL. Open installation in a new tab; recheck on return/focus and with an explicit Check again button. A GitHub callback/query-string installation ID is never proof.
- Verify with the signed-in user's existing GitHub App token: page `/user/installations`, accept only this app and non-suspended installations, then query `/user/installations/:id/repositories` until at least one readable repository is confirmed. Bound the overall check, and report upstream/configuration failure distinctly from no installation. An organization approval request without an active installation is not completion.
- Step 2 offers ChatGPT device login, AI Gateway key and OpenRouter key. Reuse the same provider-connection component in onboarding and account settings. Connected means our backend saved a credential, not a paid entitlement validation.
- `POST /api/onboarding/complete` takes no user-controlled completion flag. With session, Origin and CSRF checks, the backend freshly verifies GitHub eligibility and at least one stored credential, then persists completion. Recheck the provider condition in the completion transaction. A repeated eligible completion succeeds idempotently; missing requirements return a useful conflict and no flag update.
- After completion, call Better Auth `getSession({ query: { disableCookieCache: true } })` through its HTTP handler so the response reaches the browser with refreshed `Set-Cookie` headers. Update the auth client before navigating. Test the actual cookie round trip using installed Better Auth 1.7.1, not just the JSON flag.
- Completion records successful setup, not permanent repository access. Existing Git/model authorization stays authoritative. Removing the last provider clears completion in the same credential-deletion transaction and refreshes the session. Serialize completion and credential-deletion/count checks on the user row. Preserve the existing provider advisory lock, acquire it before the user row lock on deletion, and never acquire provider locks from the completion transaction. This prevents two concurrent provider deletions from both observing another credential and leaving completion true.
- A confirmed absence of any eligible installation/repository clears completion in the backend readiness path and routes to repair-onboarding. A single repository denial is not proof that all installations disappeared; refresh eligibility first. Transient upstream errors show Retry, not a durable revocation. Refresh session/cache after a real transition so `/onboarding` does not bounce to `/` on a stale true flag. Never cancel running work on repair; backend cancellation/recovery remains available even though product routes are blocked.
- Production deployment should use same-site HTTPS web/API hosts. The broker tunnel is not the browser API origin by default. Preserve localhost host consistency for development and verify actual cookie acceptance; never solve CORS by using `*` or by exposing tokens to the frontend.

### 6. Submission, navigation and lifecycle

1. Freeze a submission envelope with `crypto.randomUUID()` as `clientMessageId`, prompt, ordered attachment IDs, selected model, and initial repo/branch where appropriate. Disable duplicate sends while that envelope is pending.
2. For a new thread, keep the composer pending while POSTing directly to Fastify. Do not show the user message on the new-thread page, invent a server thread UUID or navigate before receiving the accepted thread ID.
3. On 202, bind the envelope to `{ threadId, runId }`, update/invalidate history and snapshots, and navigate to `/chat/:threadId`. Show the user message only after routing, when that thread page mounts; use the accepted envelope until the persisted message arrives. Follow-ups are already on their thread route and can display their optimistic message there without navigation. Guard late responses so a user who deliberately navigated elsewhere is not forcibly moved back.
4. Match persisted user messages by `clientMessageId` and runs by `runId`. Clear only the accepted envelope's draft, not text typed afterward. Bind each draft/upload queue to its thread or new-thread key, not the template's global `input` localStorage key.
5. Network interruption after send is an unknown outcome. Keep the envelope and a Retry submission action; resend the identical request and ID to discover the original result. Store only the pending envelope in user-scoped sessionStorage if it must survive reload, then remove it on resolution/sign-out. Editing an uncertain envelope requires resolving the original first, not reusing its ID with changed content.
6. Queued/running/waiting runs disable ordinary follow-up submission but allow drafting. Explicit Stop sends POST cancellation once and displays Cancelling until durable terminal state arrives. Unmount, navigation, offline state and SSE abort never send cancellation.
7. Render preparation, running, paused, recovery and workspace-reset notices from committed events/snapshots. A reset notice must say uncommitted files and unpushed commits may be lost. A process nonzero exit is a tool failure; ambiguous transport is not displayed as a proven stopped command.

### 7. Durable SSE and transcript reconstruction

- Open only one reader for the active thread, including idle threads so late title/workspace events can arrive. Reuse its projection on return; do not open one reader per sidebar item. Strict Mode setup/cleanup must not leak readers.
- A fresh projection starts at zero. A cached projection resumes from its own last applied sequence. Never initialize its cursor from `snapshot.latestEventId`, because that skips all tool history and partial text.
- Keep the replay projection separate from the latest snapshot. The snapshot's cursor is a watermark for summary state: replay older events to rebuild the timeline without regressing terminal run status, title or workspace generation from a newer snapshot. A stale refetch must not overwrite newer SSE facts; replay/apply the post-snapshot event tail when merging it.
- Validate SSE content type, framing, JSON and known payloads; retain split UTF-8/CRLF support, ignore heartbeats and bound unterminated buffers. Apply only increasing per-thread sequences and advance the cursor after successful projection. On a gap, reconnect from the last applied cursor. Unknown future event names can advance with an unsupported-event marker; malformed known events show a protocol error rather than retrying forever or silently dropping required content.
- Reconnect network errors and clean EOF with capped exponential backoff and jitter. Respect `Retry-After` for reader limits, stop on 401/404, and distinguish reconnecting from run failure. Refetch snapshot/questions on reconnect and invalidate history on meaningful lifecycle events.
- Identity is `(threadId, runId, attemptId, assistantAttempt, messageIndex)` for assistant text, and `(threadId, runId, attemptId, toolCallId)` for tools. Sequence is the ordering authority; attempt IDs are opaque and must not be lexicographically compared.
- Add per-assistant-message boundaries/indexes to new runner events so commentary stays on the correct side of tools. For old events without these fields, use a conservative contiguous-text fallback. On a later `assistant.started`, supersede incomplete earlier-attempt material without combining deltas across attempts. Durable questions and settled operation notices remain visible independently.
- Reconcile terminal snapshots by `message.runId`. Keep earlier committed commentary and tool cards, replace only the final streamed assistant message with the persisted final message, and never render it twice. A terminal event arriving before the refetch must not blank the last visible text.
- Failed/cancelled attempts retain clearly marked partial content instead of fabricating a final reply. Resume after a question must not erase completed prior-turn content; test continuation versus genuine failed-attempt replacement explicitly.
- Coalesce rendering updates to a frame/small batch while processing all sequences in order. Keep append-only text efficiently, parse/highlight diffs only on expansion, and preserve scroll position unless the reader is already at the bottom.
- Patch title caches immediately for the active thread. Refresh the sidebar on window focus/navigation and use low-frequency polling, initially five seconds while visible, when loaded rows have unresolved titles or active runs. This updates background-thread titles without a new user-wide SSE endpoint or extra readers.

### 8. Real bash streaming and tool presentation

#### Backend output path

- Add an optional progress observer to the coordinator-backed command call. `remote_exec` opts in; repository setup, attachments, discovery and file tools do not publish internal commands as user bash output.
- While the original fenced command is in flight, the execution coordinator polls a new read-only guest-journal progress request, initially every 500 ms with no overlapping polls. It reads only that command's bounded capture files and validates command/workspace/generation/run/attempt metadata. This is internal observation of an already admitted command, like reconciliation, not another queued workspace mutation or a second execution.
- Use explicit stdout/stderr byte offsets and bounded chunks. Decode split UTF-8 correctly, never promise exact interleaving across independently captured streams, and stop reading once the existing output cap is reached. Validate files against traversal/symlink substitution. Do not alter guest process locks, command exit detection, capture draining or final journal settlement.
- Send incremental `tool.output` payloads with command ID, call ID, stream, offset and text through the existing attempt-owned `PiPersistenceWriter`. Preserve database ownership validation and bounded admission. No stdout through Temporal and no direct provider output forwarded blindly to the browser.
- Stop and await the progress observer before terminal output. The final reconciled stdout/stderr replace the live preview rather than append to it, repairing missed progress without duplicating text. Byte-offset duplicate handling is separate from SSE sequence dedupe.
- Progress observation failure does not establish command failure or release ownership. Record a bounded progress-unavailable diagnostic and let existing command completion/reconciliation determine the outcome. A persistence failure remains fatal to the Pi attempt and requires the existing remote-command reconciliation path.
- Use the existing provider `exec` operation for journal reads, so no new Freestyle streaming SDK integration is necessary. Verify concurrent observation with provider doubles and real Docker; report live Freestyle verification separately.

#### Cards and grouping

| Tool                | Collapsed label                                           | Expanded content                                                                                                         |
| ------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `remote_exec`       | Bash and exact command, plus running/exit/error indicator | Live stdout/stderr, then final bounded output; preserve newlines and show truncation/transport diagnostics               |

- Add an explicit created/replaced fact to the guest write result and parse it through the same structured file-result path as edits. Do not infer creation from an empty before-hash, since an existing empty file is different. Bound durable write-argument previews, include original byte count/truncation, and keep the unchanged full arguments in the Pi checkpoint. Only mark a file successfully created after its completed result.
- Preserve structured public web results from `AgentToolResult.details` through an allowlisted schema. Today Pi stringifies and can truncate the wrapper into invalid JSON. Old stringified results get a validated legacy decoder with plain-text fallback; new results preserve the already bounded search/fetch shapes.
- A truncated or malformed patch may not parse. Render its available text with a Truncated diff notice instead of crashing Pierre or fetching unseen workspace files. No fabricated diff on a failed edit. Mount expensive renderers lazily and use stable per-call keys.
- Group only adjacent compatible calls within the same run/attempt and assistant-message interval. Reads/list/search form an Exploring group inspired by Codex. Deduplicate path labels, not actual calls. For shell classification use only conservative simple command matches; compound/unknown commands stay Bash. Classification never changes execution permissions.
- Consecutive edits/writes can share a File changes group, web calls a Web research group, and consecutive ordinary shell calls a Bash commands group. Keep each command/file row addressable and expandable inside its group. First-call identity is the stable group key, so new arrivals do not collapse an open row.
- Assistant text, questions, approvals, errors, run/attempt changes and terminal boundaries close a group. Do not hide errors in a successful aggregate. Read-only groups remain compact visible labels without an output expander.
- Treat shell, repository and web content as untrusted. Escape code, reject unsafe link schemes, disable raw HTML and automatic remote-image loads in fetched Markdown, and never render terminal escape sequences as executable HTML.
